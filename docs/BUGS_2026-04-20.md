# Operational Bugs — 2026-04-20

Three production-facing bugs in the cashroom workflow surfaced during post-deploy review of `feat/in-app-user-guides`. All three are related to **business-day awareness and time handling** — the system currently treats every calendar day as a working day and every timestamp as UTC, which produces visible user pain (3 AM emails, artificially low compliance rates, spurious "missed submission" flags on weekends).

All three are fixed on branch **`fix/cashroom-weekend-closure-tz`**.

---

## Issue #3 — Daily reminder emails sent at ~3 AM local

### Symptoms
US-based operators (`@compass-usa.com`) receive the daily submission reminder email at **3 AM US Central (CDT)** or **2 AM CST**. Almost every operator ignores/misses it because it arrives overnight. Controllers receive the visit reminder at the same unreasonable hour.

### Root cause
`backend/app/services/scheduler.py`:

```python
_scheduler.add_job(
    job_daily_reminder,
    CronTrigger(hour=int(hour), minute=int(minute)),  # no timezone=!
    ...
)
```

1. `CronTrigger` defaults to the **container's local time**.
2. The prod backend container has **no `TZ` env var** and no `/etc/timezone` → runs in **UTC**.
3. Config default `daily_reminder_time = "08:00"` therefore resolves to **08:00 UTC**, which is **03:00 CDT / 02:00 CST / 04:00 EDT**.

The `job_visit_reminder` is worse — hardcoded at `CronTrigger(hour=8, minute=0)`, not even configurable.

### Proposed fix
Two-part fix:

1. **Scheduler TZ awareness** (`backend/app/services/scheduler.py`):
   - Add a `scheduler_timezone` column to `system_config` (default `America/Chicago` for US ops; deployments elsewhere can override).
   - Pass `timezone=ZoneInfo(cfg.scheduler_timezone)` to each `CronTrigger`.
   - Log the effective trigger time in local time on scheduler start for sanity.

2. **Prod env hardening** (`docker-compose.yml` on prod + `.env.example` in repo):
   - Add `TZ: "America/Chicago"` to the `backend` service so any non-APScheduler `datetime.now()` without explicit tz also behaves correctly. Belt-and-suspenders.

### Affected files
- `backend/app/models/config.py` — add column
- `backend/app/schemas/config.py` — expose in API
- `backend/app/api/v1/admin.py` — allow admin to edit via PATCH /system-config
- `backend/app/services/scheduler.py` — use tz-aware CronTrigger
- `backend/alembic/versions/…_add_scheduler_timezone.py` — new migration
- `docker-compose.yml` (prod) — add `TZ` env var

### Risk / impact
- **Low.** Migration is additive (new column with default). SLA arithmetic is already UTC-based — unchanged. Only the cron firing time moves.
- **Side effect** once deployed: operators will receive their first correctly-timed reminder the morning after deploy. Any reminder that "should have" fired at 08:00 UTC on deploy day and hasn't yet will skip (APScheduler `misfire_grace_time=3600` already set).

### Verification
- Unit: mock `cfg.scheduler_timezone = "America/Chicago"`, assert next_run_time is 08:00 CDT.
- Manual on prod: log in as admin, set scheduler_timezone, restart backend, inspect `_scheduler.get_jobs()[0].next_run_time` — should be future 08:00 CDT.

## Issue #1 — Weekend days produce false "missed submission" flags

### Symptoms
Cashroom operators don't work Saturdays or Sundays. The system currently expects a submission every day. Every weekend produces two "missed" rows per location, reminder emails fire on weekend mornings (on top of the 3 AM problem from #3), and compliance rate is artificially dragged down by ~28% (2/7 days always missing).

### Root cause
Only `backend/app/api/v1/verifications.py` has any Mon-Fri awareness — it blocks controller visits on weekends. Missed-submission logic, reminder scheduler, SLA arithmetic, and compliance denominators all treat all 7 days identically.

### Proposed fix

1. **New helper**: `backend/app/core/business_days.py`
   ```python
   from datetime import date, timedelta
   WEEKEND = {5, 6}  # Saturday, Sunday (Python weekday(): Mon=0)
   def is_business_day(d: date) -> bool: return d.weekday() not in WEEKEND
   def next_business_day(d: date) -> date: ...
   def prev_business_day(d: date) -> date: ...
   def business_days_between(start: date, end: date) -> int: ...
   ```

2. **Apply in scheduler** (`scheduler.py`):
   - `job_daily_reminder` — bail early if `not is_business_day(today)`.
   - `job_visit_reminder` — same guard.

3. **Apply in missed-submission auto-flag** (`submissions.py`, `admin.py` wherever `MissedSubmission` rows are created):
   - Skip weekend dates entirely — no row written.

4. **Apply in SLA breach check** (`scheduler.py`):
   - Replace `datetime.now(timezone.utc) - timedelta(hours=sla)` with a business-day-aware cutoff so a Friday 17:00 submission doesn't breach on Sunday 17:00.

5. **Apply in compliance denominators** (`backend/app/api/v1/compliance.py`, any reports code):
   - `expected_submissions_count = business_days_in_period(start, end)` instead of `(end - start).days`.

### Affected files
- `backend/app/core/business_days.py` (new)
- `backend/app/services/scheduler.py` — 3 call sites
- `backend/app/api/v1/submissions.py` — missed-flag logic
- `backend/app/api/v1/admin.py` — backfill missed-flag logic
- `backend/app/api/v1/compliance.py` — denominator math
- `backend/tests/test_business_days.py` (new)
- `frontend/src/pages/regional-controller/RcBizDash.tsx` — "days since submission" should count business days
- `frontend/src/pages/operator/OpStart.tsx` — disable Sat/Sun in date pickers where operator picks a "for date"

### Risk / impact
- **Medium.** Pure logic change. No data migration. No deletion of historical weekend "missed" records — they stay for audit but a display filter hides them from current-month compliance rate.
- **Side effect**: compliance rate will jump ~28% overnight once deployed (weekends stop dragging it down). Stakeholders should be notified that the jump is the fix, not a data change.
- **Edge case**: if someone DOES submit on a Saturday (volunteer count during audit week), the submission still accepts — we're not blocking the submit endpoint, only the auto-flag/reminder/denominator logic.

### Verification
- Unit: `is_business_day` cases for Mon–Sun, boundary timestamps, DST handling (though Python `date` is tz-naive — acceptable).
- Integration: create a submission on Friday, verify SLA breach doesn't fire until Tuesday.
- Manual: check RcBizDash compliance-rate KPI before/after fix against known data.

## Issue #2 — No way to report legitimate Mon-Fri closures

### Symptoms
When a cashroom is legitimately closed on a weekday (public holiday, weather, power outage, audit day), there's no way to say so. It shows up as a missed submission, drags compliance rate, fires reminders. Operators have no mechanism to communicate "today was closed, don't flag it".

### Root cause
No concept of "no count expected" in the data model. The only non-submission path is "missed".

### Proposed fix

1. **New model**: `backend/app/models/closure.py`
   ```
   closure_records
   ├── id                UUID
   ├── location_id       FK → locations
   ├── date              DATE          (Mon-Fri only, app-layer validation)
   ├── reason            ENUM          ['HOLIDAY', 'WEATHER', 'OTHER']
   ├── notes             TEXT          (required if reason='OTHER')
   ├── reported_by_id    FK → users
   ├── reported_at       TIMESTAMPTZ
   ├── unique (location_id, date)
   ```

2. **Alembic migration** — additive, no backfill of existing data.

3. **API endpoints** (`backend/app/api/v1/closures.py` new):
   - `POST /v1/closures` — create (operator+)
   - `GET /v1/closures?location_id=&from=&to=` — list
   - `PATCH /v1/closures/{id}` — edit (same user or admin)
   - `DELETE /v1/closures/{id}` — remove (admin, or within 15min of create)

4. **Integration with missed-submission auto-flag**: skip any date where a closure exists for that location.

5. **Integration with compliance**: closures count as **satisfied** in the compliance-rate numerator (treating them like an approved submission for rate purposes). Alternative: exclude from both num and denom — confirm with stakeholders.

6. **Audit**: emit `CLOSURE_REPORTED` / `CLOSURE_EDITED` / `CLOSURE_DELETED` events.

7. **Frontend**:
   - **Operator dashboard** (`frontend/src/pages/operator/OpStart.tsx`) — add a secondary button `Report no count →` next to `Submit Now`. Modal: date (today, read-only), reason radio (Holiday/Weather/Other), notes field (required if Other).
   - **Operator history table** — new status badge `No Count · Holiday` / `Weather` / `Other`.
   - **RC Location Review** (`frontend/src/pages/regional-controller/RcLocationReview.tsx`) — show `🗓 Closed — {reason}` pill in the Submissions Today column.
   - **Admin** — new panel `AdmClosures.tsx` for retroactive/backfill closure reporting.

### Affected files
- `backend/app/models/closure.py` (new)
- `backend/app/schemas/closure.py` (new)
- `backend/app/api/v1/closures.py` (new)
- `backend/app/api/v1/router.py` — register new router
- `backend/alembic/versions/…_add_closures.py` — new migration
- `backend/app/api/v1/submissions.py` — missed-flag integration
- `backend/app/api/v1/compliance.py` — compliance integration
- `backend/app/services/audit.py` — emit new event types

- `frontend/src/api/closures.ts` (new)

- `frontend/src/pages/operator/OpClosureModal.tsx` (new)
- `frontend/src/pages/regional-controller/RcLocationReview.tsx` — closure pill
- `frontend/src/pages/admin/AdmClosures.tsx` (new) — optional, can defer

### Open questions (to confirm before coding)

1. **Approval flow** — does a closure need a controller to approve (like a regular submission), or does it auto-accept? Recommend: auto-accept for HOLIDAY/WEATHER, controller-review for OTHER.
2. **Compliance math** — closure counts as compliant (simpler) vs excluded from denominator (cleaner for very-closed cashrooms). Recommend: counts as compliant.
3. **Backfill window** — can a closure be reported for any past date, or only within current week? Recommend: within 30 days for operators, unlimited for admins.
4. **Submission-vs-closure exclusivity** — if a closure exists and then a submission comes in the same day, what happens? Recommend: submission deletes the closure (late real count trumps early "no count").

### Risk / impact
- **Medium.** New schema, new endpoints, three frontend touches. Additive throughout.
- **Side effect**: once deployed, operators can report closures retroactively for the current week — expect a flurry of backfill on Monday as they catch up on past weeks' holidays.

### Verification
- Unit: reason validation, notes-required-if-other, Mon-Fri-only date, location_id+date uniqueness.
- Integration: create closure → verify missed-submission isn't flagged, compliance rate counts as satisfied.
- E2E: operator creates closure from dashboard → RC sees pill in Location Review → admin edits → audit trail shows events.
